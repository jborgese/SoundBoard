# Working in this repository

SoundBoard is a WPF soundboard for Windows, targeting **.NET Framework 4.8**. It ships as a
single portable `SoundBoard.exe` (Costura embeds every dependency) with an in-app updater that
polls `VersionInfo.xml` on `master`. That shape drives most of the rules below: there is no
package to hotfix, and every tag is offered to existing installs.

[`BUILDING.md`](BUILDING.md) is the reference for the build, the projects and the release
scheme. This file is the short list of things that are easy to get wrong.

## Build and test

```powershell
msbuild SoundBoard.sln /restore /p:Configuration=Debug /m
vstest.console.exe SoundBoard.Tests\bin\Debug\SoundBoard.Tests.dll
```

**`dotnet build` cannot build this solution** — it needs full MSBuild from Visual Studio
(classic `.csproj`, a `stdole` COM reference, and WPF targets). `dotnet build` works on the
SDK-style class libraries alone, but not on the app or the test project.

## Things that will bite you

**Adding a `.cs` file under `SoundBoard/` needs a `<Compile Include="…" />` in
`SoundBoard.csproj`.** That project is classic-format, not SDK-style, so new files are *not*
picked up automatically — the build fails with `CS0103: The name … does not exist`.
`SoundBoard.Model` and `SoundBoard.Tests` are SDK-style and do glob.

**Never hand-edit a version.** The git tag is the only source of truth; `Version.targets`
stamps the build, and `SoundBoard/VersionInfo.xml` is generated by the release workflow.

**`CHANGELOG.md` gates the release.** The workflow fails if the tag has no `## [X.Y.Z]`
section, because that section becomes both the GitHub Release body and the update manifest's
`<VersionNotes>`. Add user-visible changes under `## [Unreleased]` as you go.

**Do not run the app with a `soundboard.config` in its working directory** unless you mean to.
`ConfigStore.LoadWithLegacyMigration` treats one as a pre-1.3 config: it loads it and saves it
**over** `%AppData%\SoundBoard\soundboard.config`. To run against a scratch board, use the
switch that exists for it:

```powershell
SoundBoard.exe --config C:\path\to\scratch.config
```

That points every read, write, `.bak` and `.temp` at the named file and skips the legacy
migration entirely, so the real board is never touched.

## Localization

Every user-visible string lives in `SoundBoard/Properties/Resources.resx`, with a translation
in `Resources.es.resx`. `SoundBoard.Tests/LocalizationTests.cs` enforces that they stay in
step — no missing strings, no stale ones, the same `{0}` placeholders, and no string that only
makes sense concatenated with another. Adding an English string without its Spanish
counterpart fails the build's tests.

Two gotchas:

- **`Resources.Designer.cs` is hand-maintained.** Add the property alongside the `.resx` entry;
  it is not regenerated by the build.
- **The `.resx` files are CRLF and Git Bash `sed` silently strips that.** Edit them with
  PowerShell, or with a tool that preserves line endings.

## UI conventions

Sound buttons build their `Style` in code rather than through `DynamicResource`, so two rules
follow that nothing enforces for you:

- **`SoundButtonStyle.IsLightBackground` is the single answer to "black or white on this
  button?"** Read that, never `IsLightColor` directly. `IsLightColor` is null for a sound with
  no colour of its own, and treating that null as "light" paints black controls on a near-black
  button in the Dark theme.
- **A sound button does not follow a live theme change on its own.** `MainWindow` calls
  `SoundButton.Restyle()` on every button when the theme switches; anything drawn per-button
  has to be rebuilt inside `SetUpStyle` to be picked up.

## Tests

`SoundBoard.Tests` references the **executable** (via `InternalsVisibleTo`), which is why the
test project cannot be built with `dotnet build` either. Some tests spawn real processes and
touch real paths, so when one fails only on CI, check whether its fixture's precondition still
holds before writing it off as flaky.
